## 2. Формальное описание ядра исполнения

Реализовано в `DZ_NTSIM_Engine.py`.

### 2.1. Путь цены внутри бара

Бар k с ценами O, H, L, C проходится тремя отрезками:

```
P = (O → E1, E1 → E2, E2 → C),  где  E1 = H, E2 = L, если бар «двинулся вверх первым»
                                      E1 = L, E2 = H — иначе
```

**Правило «вверх первым» руководство не раскрывает.** Реализованы два кандидата, выбор — калибровкой:

```
closer:    вверх первым ⇔ (H − O) ≤ (O − L)      ближний к открытию экстремум первым
closeopen: вверх первым ⇔ C ≥ O
```

### 2.2. Набор ордеров

Набор рабочих ордеров Wₖ фиксируется на начало бара k. Ордер, поданный в `on_bar_update` при закрытии бара k, входит в Wₖ₊₁. Входной ордер, не подтверждённый стратегией на следующем баре, снимается — поведение `isLiveUntilCancelled = false`.

### 2.3. Исполнение на отрезке a → b

| Ордер | Условие | Цена |
|---|---|---|
| Рыночный | первый отрезок | a |
| Стоп на покупку S | a ≥ S | a — разрыв |
| | иначе max(a, b) ≥ S | S |
| Стоп на продажу S | a ≤ S | a — разрыв |
| | иначе min(a, b) ≤ S | S |
| Лимит на покупку L | min(a, b) < L — пробой; ≤ L при касании | L |
| Лимит на продажу L | max(a, b) > L — пробой; ≥ L при касании | L |

Цена лимита — по руководству: «set the fill price to the current order's Limit price». **Требуется ли пробой или хватает касания — калибруется.**

**Проскальзывание** s тиков — только для рыночных и стоповых исполнений, против позиции, в пределах бара:

```
fill_buy  = min(fill + s·tick, Hₖ)
fill_sell = max(fill − s·tick, Lₖ)
```

### 2.4. Позиция и результат

| Правило | Реализация |
|---|---|
| Разворот | закрытие и открытие по одной цене |
| Стоп и цель | выставляются от цены исполнения входа; действуют со следующего бара |
| Выход на баре входа | не моделируется — **калибруется** |
| Стоп и цель | взаимно отменяющие; исполнение одного снимает другой |
| Закрытие сессии | по закрытию последнего бара сессии |
| Результат | (выход − вход)·сторона·объём·PointValue − 2·комиссия_за_сторону·объём |

### 2.5. Три нераскрытых правила и их калибровка

| Правило | Кандидаты | Как выбирается |
|---|---|---|
| Направление первого движения бара | closer, closeopen | `calibrate` против выгрузки Strategy Analyzer |
| Лимит: пробой или касание | through, touch | то же |
| Выход на баре входа | нет, да | по расхождениям сверки |

## 3. Факторы паритета вне алгоритма

Каждый обязан совпадать с настройкой прогона в NinjaTrader:

1. **Источник данных** — только выгрузка из самого NinjaTrader; бары другого поставщика отличаются.
2. **Merge Policy** склейки контрактов — меняет исторические цены.
3. **TickSize и PointValue** — из Instrument Manager, не из биржевой спецификации.
4. **Шаблон торговых часов** — границы сессий и закрытие по сессии.
5. **Шаблон комиссии.**
6. **Проскальзывание** в тиках.
7. **Order Fill Resolution** — Standard или High.
8. **Calculate** — OnBarClose.
9. **BarsRequiredToTrade, EntriesPerDirection, EntryHandling.**

## 4. Критерии приёмки паритета

Для каждого инструмента:

| Критерий | Порог |
|---|---|
| Число сделок | равно |
| Сопоставление | каждая сделка по времени входа (±1 бар) и направлению |
| Результат сделки | \|ΔP&L\| ≤ 0,005 |
| Неоднозначность | если исполнений, зависящих от пути внутри бара, больше 5% — повторная сверка с Order Fill Resolution «High» |
| Фиксация | результат калибровки записывается в журнал ревизии |

**Первый инструмент — MGC, стратегия — встроенная `@SampleMACrossOver`.** Её логика однозначна, поэтому любое расхождение относится к исполнению, а не к логике.

## 5. Поправки к фактам меморандума и плана

**«Паритет 194/194»** — это самопроверка инструмента сверки на синтетике: движок сравнивался **сам с собой**. Паритет с NinjaTrader не проверялся ни разу.

**«Генерация безошибочного кода».** Код не безошибочен. За эту работу: ошибка компиляции `CS0246` с типом `ATR`; дефект Д-23 в эталоне, пропущенный всеми проверками чтением; ряд дефектов, найденных только запуском. Код — гипотеза, пока он не скомпилирован и не прогнан.

**Excel** принимается как пульт, который **формирует** `task.json`. Источник истины — JSON: он читается в Git построчно.

**Режим 2.** Связи параметров объявляются в графе с обоснованием каждой, а не выводятся. Файла `DZ_SW_S021_11_Карта_связей_настроек.md` среди выданных нет. Граф существует для одной стратегии: `DZ_OPT_Graph_DualBreakout.json`.

**280 настроек коммутатора** в движке не реплицируются. Движок исполняет стратегии, у которых есть эталонная реализация на Python. Каждый перенос требует перекрёстной сверки с NinjaTrader.

**Выгрузка XML** — правка шаблона, сохранённого самим NinjaTrader, а не генерация с нуля.

## 6. Поправки к регламенту четырёхстороннего конвейера

**Обязательная ступень «Исполнение»** между генерацией кода и его приёмкой:

```
[Генерация кода] → [ИСПОЛНЕНИЕ: компиляция в NinjaTrader — ноль ошибок;
                    прогон без ордеров; [HUB-ИТОГ]: отправлено = принято,
                    потерь 0, отказов 0] → [Ревью] → [Приёмка]
```

Ревью документов её не заменяет: дефект Д-23 прошёл все проверки чтением и обнаружился только при запуске.

**Правило доказательности.** Любое числовое утверждение — PF, доля прибыльных, точность, паритет — принимается только вместе с файлами, которые его породили: `summary.json`, `trades.csv`, отпечаток данных `sha256`, версия скрипта.

**Разрешение разногласий — измерением.** Если участники расходятся, сначала определяется проверка, способная решить спор, и она выполняется. Примеры: контроль на случайном блуждании, сверка сделка к сделке.

**Реестр испытаний.** Каждая оптимизация, в том числе запущенная из Excel, записывается. Дефлированный Шарп считается по совокупному числу испытаний.

**Одна вычислительная величина — один источник.** Вторая реализация той же логики допускается только с перекрёстной сверкой: дефекты Д-10 и Д-11 возникли именно из двух копий одного расчёта.

## 7. Следующий шаг

Он не требует генерации кода:

1. Скомпилировать текущий комплект в NinjaTrader.
2. Выгрузить минутки MGC за три месяца из NinjaTrader.
3. Прогнать `@SampleMACrossOver` в Strategy Analyzer: Fast 10, Slow 25, проскальзывание 0; выгрузить сделки.
4. `python DZ_NTSIM_Engine.py calibrate --data mgc_export.txt --instrument MGC --nt-trades sa_trades.csv`

Результат калибровки определяет, можно ли строить на движке оптимизацию.
